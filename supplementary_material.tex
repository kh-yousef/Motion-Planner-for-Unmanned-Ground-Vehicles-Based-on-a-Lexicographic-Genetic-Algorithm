\section{Path-Decoding Procedures of the Motion-Planning Problem}

The solutions $\Psi$ generated by the method describe UGV paths in polar, motion-based representation by using relative turning angles and segment lengths. However, the geometrical properties of the objective functions and constraints require calculations in task space (i.e., with Cartesian coordinates). This operation is called path encoding.

A candidate solution is composed of $n$ path segments. Each segment $s$ is described by a relative turning angle $\theta_i$ and a segment length $l_i$. The first segment of the path corresponds to the home-base $h$, whose pose is defined by its Cartesian coordinates and initial heading. Starting from the home-base pose, each subsequent segment is obtained by updating the current heading based on the relative turning angle, then translating the vehicle by the corresponding segment length.

\subsection{From Motion Representation to Task Space}
The polar representation $\zeta^p$ of a solution contains the sequence of relative turning angles and segment lengths. The decoded representation $\zeta^p$ contains the Cartesian coordinates of the path nodes. Since a path with $n$ segments contains the home node and one endpoint for each segment, $\zeta^p$ is represented with ($n$+1) rows and two columns. 

Algorithm \ref{alg:path_transform} shows the decoding procedure. It takes the path representation in motion space $\zeta^p$, the maximum number of segments $n$, and the home-base pose $h$ as input. It returns the path in task space $\zeta^c$ together with the cumulative heading vector $\Phi$. The cumulative heading vector is used for procedures, such as terminal-orientation and turning-direction checking.


\begin{algorithm}[h]
\caption{Path Transformation from Motion Space to Task Space}
\label{alg:path_transform}
\SetKwInput{Input}{input}
\SetKwInput{Output}{output}
\Input{$\zeta^p$, a matrix ($n \times 2$) of a path in motion space}
\Input{$n$, maximum number of path segments}
\Input{$h$, a vector ($1 \times 3$) with the home-base pose $(x_h, y_h, \phi_h)$}
\Output{$\zeta^c$, a matrix ($(n+1) \times 2$) of the path in task space}
\Output{$\Phi$, a vector ($1 \times (n+1)$) of cumulative headings}
\BlankLine
\Begin{
    $\zeta^c \leftarrow 0_{(n+1)\times 2}$\;
    $\Phi \leftarrow 0_{1\times(n+1)}$\;
    $\zeta^c_1 \leftarrow [h_1, h_2]$\;
    $\phi \leftarrow h_3$\;
    $\Phi_1 \leftarrow \phi$\;
    \For{$i \leftarrow 1$ \KwTo $n$}{
        $\theta \leftarrow \zeta^p_{i,1}$\;
        $l \leftarrow \zeta^p_{i,2}$\;
        $\phi \leftarrow \text{wrapToPi}(\phi + \theta)$\;
        $\zeta^c_{i+1,1} \leftarrow \zeta^c_{i,1} + l\cos(\phi)$\;
        $\zeta^c_{i+1,2} \leftarrow \zeta^c_{i,2} + l\sin(\phi)$\;
        $\Phi_{i+1} \leftarrow \phi$\;
    }
    \Return $\zeta^c, \Phi$\;
}
\end{algorithm}

The procedure follows the motion behavior of a differential-drive UGV at the planning level: the vehicle first changes its heading relative to the previous segment, then moves forward along a straight segment. Therefore, each decoded node is not an independent waypoint, but the result of a sequence of motion-consistent commands. This is important because the optimizer does not search directly over arbitrary Cartesian waypoints. Instead, it searches over relative heading changes and travel distances, which gives the decoded path an explicit motion interpretation.

For each segment $s$, the cumulative heading is updated recursively, with $\mathrm{wrapToPi}$ constraining the angle to the interval $[-\pi,\pi]$. The equation is defined as in Eqn. (~\ref{eq:cumulative_heading}).

\begin{equation}
\label{eq:cumulative_heading}
    \phi_i=\mathrm{wrapToPi}(\phi_{i-1}+\theta_i
\end{equation}

The Cartesian coordinates of the next node are computed as defined as in Eqn. (~\ref{eq:cartesian})
\begin{equation}
\label{eq:cartesian}
    \zeta^c_{i+1} = \zeta^c_i + l_i \begin{bmatrix} \cos(\phi_i) & \sin(\phi_i) \end{bmatrix}
\end{equation}

This makes the path dependent on the order of the encoded motion commands. Therefore, the resulting trajectory is not an arbitrary set of waypoints, but a sequence of straight movements generated from the relative turning angles. 

The path returned by the algorithm \ref{alg:path_transform} is only the raw decoded path. It may contain more segments than needed because the chromosome can store a maximum number of possible segments. For this reason, it identifies the node used as the terminal cut point and discards the unused nodes. After this, it replaces the last active segment with the corrected segment that connects the selected cut point to the target pose.
